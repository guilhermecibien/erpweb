# Pendências de modernização

Este arquivo lista o que falta atualizar no ERP com foco em **ambiente local**, sem preocupação com VPS/produção por enquanto. O objetivo aqui é tirar o sistema do estado legado: stack, dependências e frontend.

## Já modernizado

- [x] PHP 8.3 como runtime alvo, pipeline de CI atualizado para essa versão.
- [x] Dependências genéricas e bibliotecas fiscais compatibilizadas com PHP 8.3.
- [x] Laravel migrado de 8.x para 9.x, e depois de 9.x para 10.x (ver detalhes em "Atualização da stack"). Próxima parada: 10 → 11.
- [x] Laravel Mix/Webpack substituído por Vite.
- [x] Dependências principais do build frontend atualizadas, sem `npm audit` pendente na última checagem.
- [x] Corrigido carregamento de views do Superadmin e recuperado controlador do carrossel do e-commerce.

> A interface ainda usa Blade, AdminLTE e jQuery legados — o Vite modernizou o build, não a interface em si.

    - `ClienteEcommerceController` importava `App\Rules\ValidaDocumento` (validação de CPF/CNPJ) mas a classe nunca foi criada — `app/Rules` nem existia — então **qualquer** criação/edição de cliente e-commerce pelo painel ERP quebrava com 500. Criada `app/Rules/ValidaDocumento.php` reaproveitando o algoritmo de dígito verificador já duplicado em `PedidoEcommerceController::validaCPF()`/`validaCNPJ()`.
    - `ClienteEcommerceController::_validate()` fazia `Rule::unique('cliente_ecommerces')->ignore($request->id)`, mas `update()` nunca populava `$request->id` (nem o formulário de edição envia esse campo) — editar um cliente sem trocar e-mail/CPF sempre falhava a validação de unicidade contra si mesmo. Corrigido passando o `$id` da rota para `_validate()` e usando-o no `ignore()`.
    - (Mesma classe de problema do `AccountController`/`insertRevenue` já documentado acima, mas aqui só a título de nota: `PedidoEcommerceController@salvarVenda` também tem uma variável `$payment` não definida usada num `!empty($payment['paid_on'])` — inofensivo porque `empty()` engole variável indefinida, mas seria melhor removido numa limpeza futura.)
- [x] Testes de fluxos fiscais (`tests/Feature/Fiscal/CteGeracaoTest.php`, `MdfeGeracaoTest.php`, `NfeGeracaoTest.php`): validam a montagem/estrutura do XML de CT-e, MDF-e e NF-e (`CTeService::gerarCTe`/`MdfeService::gerarMDFe`/`NFeService::gerarNFe`) sem depender da SEFAZ real — XML bem formado (`SimpleXMLElement`), tags principais presentes (`infCte`/`infMDFe`/`infNFe`, `rem`/`dest`/`emit`, `ide`), CFOP interestadual correto, e isolamento entre empresas (403 ao acessar CT-e/MDF-e de outro negócio). Como os construtores de `CTeService`/`MdfeService`/`NFeService` exigem um certificado A1 válido mesmo só para montar o XML localmente (chamam `Certificate::readPfx` antes de qualquer coisa), foi criada a trait `tests/Concerns/CreatesFiscalCertificate.php`, que gera um certificado PKCS#12 autoassinado em runtime (`openssl_pkey_new`/`openssl_csr_sign`/`openssl_pkcs12_export`) — `NFePHP\Common\Certificate::readPfx` não valida CN nem validade, só faz o parse do PFX, então não há necessidade de simular um certificado real de homologação. Nenhum bug de produção encontrado. Também documentada uma pegadinha de teste (não é bug real): `App\Http\Middleware\SetSessionData` só popula a sessão `user` se ela ainda não existir, então trocar de admin (`actingAs`) entre duas empresas na mesma sessão de teste "gruda" no primeiro usuário — é preciso `flushSession()` entre as trocas. Ficou de fora (dependem de rede real com a SEFAZ, mesma pendência já registrada para homologação): `sign`, `transmitir`, `cancelar`, `cartaCorrecao`/`corrigir`, `consultar` dos três serviços, e a geração dos PDFs (DANFE/DACTE/DAMDFE, bibliotecas de renderização separadas da montagem do XML fiscal em si).
